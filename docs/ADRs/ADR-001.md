# ADR-001: PostgreSQL First; No Redis in V1

## Status
Accepted

## Context
Applications commonly need background job processing. A common architectural reflex is to prematurely introduce Redis with Celery or BullMQ. However, introducing Redis alongside an authoritative relational database results in:
1. Dual state stores with divergent failure domains.
2. Partial failure during two-phase enqueue (e.g. database commit succeeds but Redis push fails or vice-versa).
3. Complex reconciliation logic and lack of ACID transactional guarantees across job submission, tenant quota checks, and idempotency key creation.

## Decision
QueueForge uses PostgreSQL as the single, authoritative, durable source of truth for all jobs, idempotency keys, tenant rate buckets, concurrency slots, worker leases, attempt history, and recurring schedules.
Concurrency control is achieved using PostgreSQL's native `SELECT ... FOR UPDATE SKIP LOCKED` inside short, bounded transactions. User task handlers execute strictly outside database transactions.

## Consequences
- **Positive:** Absolute atomicity between job submission, idempotency recording, and tenant quota accounting. Zero dual-write discrepancies. Low operational complexity for single-VPS and small-team deployments.
- **Positive:** Reliable state recovery and inspection via standard SQL tools.
- **Negative / Trade-offs:** Throughput is bounded by PostgreSQL row-locking and connection pool capacity rather than in-memory message broker speeds. Measured on a 1-vCPU box with Postgres co-located: ~700-900 enqueues/sec and ~390 jobs/sec drained by 4 workers (see docs/benchmark-reports/report.md).
- **Trigger for Re-evaluation:** A future migration to Redis or dedicated queue brokers will only be considered via a new ADR backed by empirical production benchmarks showing database lock contention saturation.
