# ADR-003: Direct PostgreSQL Worker Claims via FOR UPDATE SKIP LOCKED

## Status
Accepted

## Context
Worker processes need to coordinate claiming eligible queued jobs without race conditions, duplicate leases, or lock blocking that causes deadlocks and serialization failures under high concurrency.

## Decision
Workers poll PostgreSQL and claim work directly using `SELECT ... FOR UPDATE SKIP LOCKED`. 
- The claim transaction locks an eligible queued job and an available tenant execution slot in a single, short ACID transaction.
- It transitions the job status to `running`, sets a fresh cryptographic UUID lease token, and inserts a `job_attempts` record.
- **Critical rule:** The transaction immediately commits before the user task handler function begins execution.

## Consequences
- **Positive:** Zero worker blocking—competing workers skip locked rows smoothly, resulting in linear horizontal worker scaling.
- **Positive:** Database connections and locks are held only for microseconds during claim and result commit, never during slow handler network or CPU work.
- **Negative / Trade-offs:** Workers require direct PostgreSQL network connectivity. A private network or TLS connection string is required.
