# ADR-005: Strict Priority Ordering in V1

## Status
Accepted

## Context
Jobs in QueueForge support an integer priority from 0 (lowest) to 9 (highest), defaulting to 5. The queue engine needs a deterministic claiming order across priority tiers.

## Decision
QueueForge v1 uses strict priority ordering:
`ORDER BY j.priority DESC, j.run_at ASC, j.created_at ASC, j.id ASC`
Workers always claim eligible higher-priority work before lower-priority work.

## Consequences
- **Positive:** Intuitive, deterministic behavior for latency-critical tasks (e.g. priority 9 user verification codes will jump ahead of priority 2 weekly digest reports).
- **Positive:** Index-supported query plan utilizing the composite partial index `jobs_claim_idx`.
- **Negative / Trade-offs:** Under sustained saturation of high-priority jobs, low-priority jobs can experience starvation. Operators should isolate different traffic tiers using distinct queue names (`notifications`, `background`, `maintenance`) or monitor queue wait times by priority.
- **Future Work:** Weighted round-robin or priority aging will be evaluated if multi-priority contention benchmarks show severe starvation.
