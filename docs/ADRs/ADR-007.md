# ADR-007: Tenant Quota Implementation and Execution Slots

## Status
Accepted

## Context
In a multi-tenant environment, a single misbehaving or runaway tenant could flood the queue with millions of jobs, consume all worker execution capacity, and exhaust database connections, starving other tenants.

## Decision
QueueForge implements a 3-layer quota defense system in PostgreSQL:
1. **Submission Rate Limiting:** Stored token bucket in `tenant_rate_buckets`. Every new enqueue transaction locks the bucket row, calculates token refill based on elapsed time (`rate_per_second`), and enforces `burst_capacity`. Deficits return `429 Too Many Requests` with a calculated `Retry-After`.
2. **Backlog Cap:** Transactional `tenant_usage.outstanding_jobs` counter. Enqueue checks `outstanding_jobs < max_pending_jobs` and increments it. Decremented when a job reaches any terminal state (`succeeded`, `dead`, `cancelled`).
3. **Execution Concurrency Slots:** Pre-provisioned physical rows in `tenant_execution_slots`. Workers claim an eligible job and reserve a free slot (`WHERE current_job_id IS NULL AND enabled = true`) in the same transaction using `FOR UPDATE SKIP LOCKED`.

## Consequences
- **Positive:** Absolute hard limit on concurrent running jobs per tenant. Zero race condition oversubscription.
- **Positive:** Multi-replica API and worker servers share identical global quota state via PostgreSQL transactions without requiring distributed lock managers.
- **Negative / Trade-offs:** Row locks on `tenant_rate_buckets` serialize enqueue requests for the same tenant. Benchmarks show this comfortably handles 400+ ops/sec per tenant.
