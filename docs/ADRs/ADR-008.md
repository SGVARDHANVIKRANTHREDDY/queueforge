# ADR-008: Retention and Replay Semantics

## Status
Accepted

## Context
High-volume queues accumulate large volumes of terminal jobs, attempt logs, audit events, and idempotency keys over time. Without automated retention, tables bloat, indexes degrade, and query performance suffers. Additionally, operators need safe replay semantics for dead-lettered jobs.

## Decision
1. **Retention Periods:**
   - Terminal jobs (`succeeded`, `dead`, `cancelled`) and their child `job_attempts` / `job_audit_events`: 30 days (`QF_TERMINAL_JOB_RETENTION`).
   - Idempotency keys: 24 hours (`QF_IDEMPOTENCY_TTL`).
   - Validation invariant: `QF_TERMINAL_JOB_RETENTION >= QF_IDEMPOTENCY_TTL` ensures idempotency rows never outlive their target jobs.
2. **Batch Sweeping:** A background retention loop purges expired records in bounded batches (500 rows per transaction) to prevent table locking and transaction log bloat.
3. **Dead-Letter Replay:**
   - Only jobs with `status = 'dead'` can be replayed.
   - Replay preserves prior attempt history, increments `replay_generation`, resets `attempts_started = 0`, sets `status = 'queued'`, and records an auditable event in `job_audit_events`.
   - The original idempotency key continues to map to the replayed job.

## Consequences
- **Positive:** Bounded database footprint while preserving sufficient audit and debug history.
- **Positive:** Replay is 100% auditable and clean—past failures are not erased.
- **Negative / Trade-offs:** Deleting terminal jobs means historical jobs older than 30 days are purged. If long-term compliance storage is needed, an external warehouse dump should be used.
