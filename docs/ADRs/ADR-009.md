# ADR-009: API Key Storage, Issuance, and Permissions

## Status
Accepted

## Context
Tenant authentication must be cryptographically secure, resilient against database leaks, and support granular role-based access without storing reversible plaintext secrets.

## Decision
1. **Secret Generation:** API keys are generated using 256 bits of cryptographically secure random entropy (`crypto/rand`) formatted with a recognizable prefix (`qf_live_<base64url>`).
2. **Storage:** Only the SHA-256 hash of the secret token is stored in `api_keys.secret_hash`. The raw secret is displayed exactly once to the operator upon creation and never stored or logged anywhere in QueueForge.
3. **Display Prefix:** A non-secret prefix (e.g. `qf_live_AbCd...`) is retained for audit logging and key identification.
4. **Permissions:** Scoped granular permission arrays (`jobs:read`, `jobs:write`, `schedules:read`, `schedules:write`, `deadletters:read`, `deadletters:write`, `metrics:read`) enforced at the HTTP middleware layer.
5. **Revocation:** An explicit `revoked_at` timestamp immediately invalidates subsequent authentication attempts.

## Consequences
- **Positive:** Even if a database backup is compromised or exposed, attacker cannot retrieve usable credentials.
- **Positive:** Operators have granular capability to revoke compromised keys instantly.
- **Negative / Trade-offs:** If a client loses their API key secret, it cannot be recovered; the operator must revoke the lost key and issue a new one.
