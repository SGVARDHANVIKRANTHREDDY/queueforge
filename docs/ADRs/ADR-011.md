# ADR-011: LISTEN/NOTIFY as a Wake-Up Hint, Polling as the Source of Truth

## Status
Accepted

## Context
Workers originally discovered work only by polling every `QF_CLAIM_POLL_INTERVAL` (250 ms) and claimed **one job per tick**. Two measured consequences on the same machine, same code otherwise:
- Throughput ceiling of `1000/poll_ms` = 4 jobs/sec **per worker** (16 jobs/sec with 4 workers), regardless of handler speed.
- Idle end-to-end latency (enqueue -> succeeded) p50 = 222 ms, dominated by waiting for the next tick.

## Decision
1. `EnqueueJob` issues `pg_notify('qf_jobs', queue)` inside its transaction. Postgres delivers it only if the transaction commits, so a worker is never woken for a job that does not exist.
2. Each worker holds one dedicated connection in `LISTEN` and feeds a 1-slot coalescing channel that wakes `claimLoop`.
3. `claimLoop` keeps claiming until nothing is claimable or the process hit `QF_WORKER_CONCURRENCY`, and re-wakes itself whenever a job finishes (a tenant slot and a concurrency slot just freed up).
4. **Polling is retained.** NOTIFY is best-effort (a disconnected listener misses it) and delayed/retried jobs become runnable by the passage of time, not by an event.

## Consequences
- **Positive (measured):** drain throughput 16 -> 387 jobs/sec (4 workers); idle e2e p50 222 ms -> 6.8 ms.
- **Positive:** correctness does not depend on NOTIFY. Losing every notification only degrades latency to the old polling behaviour.
- **Negative:** one extra statement per enqueue (enqueue throughput measured ~10-20% lower in noisy single-vCPU runs) and one held connection per worker.
- **Negative:** NOTIFY goes through a single global lock at commit in Postgres; at very high enqueue rates this becomes a contention point. Mitigation if it ever shows up: batch/skip the notify when workers are known busy.
