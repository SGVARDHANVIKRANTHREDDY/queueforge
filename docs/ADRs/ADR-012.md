# ADR-012: Recover Each Expired Lease in Its Own Transaction

## Status
Accepted (supersedes the batch-transaction approach in the first implementation)

## Context
`RecoverExpiredLeases` originally locked a batch of expired jobs and processed all of them inside **one** transaction, ignoring statement errors (`_, _ = tx.Exec(...)`). In PostgreSQL the first failed statement aborts the entire transaction; every later statement fails and `COMMIT` becomes a rollback. A single bad row therefore rolled back every recovery in the batch, on every tick, indefinitely: a poison pill that stalls all crash recovery.

Reproduced by `tests/regression: TestRecovery_PoisonJobDoesNotBlockHealthyJobs` (a trigger makes one row's update fail). It recovered 0 jobs before the fix.

## Decision
Select candidate ids without locking, then recover each in its own short transaction that re-checks `lease_expires_at <= now()` under `FOR UPDATE SKIP LOCKED`. Errors are collected with `errors.Join` and returned/logged; healthy rows still recover. Retry-vs-dead logic lives in one function, `settleFailedAttempt`, shared with the handler-failure path so the two cannot drift.

## Consequences
- A poison row is isolated and visible (error returned and logged) instead of silently blocking everything.
- A worker that renewed or completed at the last instant wins: the re-check under the row lock leaves its job alone.
- One transaction per recovered job instead of one per batch; recovery is a rare path so the cost is irrelevant.
- Known limit: if >= `batchSize` poison rows sort first by `lease_expires_at` they can still occupy the whole batch. They are surfaced via the returned error and should be fixed by an operator; acceptable for v1.
