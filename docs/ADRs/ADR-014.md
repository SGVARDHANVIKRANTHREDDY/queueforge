# ADR-014: The Database Is the Only Clock

## Status
Accepted

## Context
Several machines make time-based decisions in this system: API servers (when is this job due?), workers (has my lease expired?), schedulers (which cron occurrence is next?), and the database. Machine clocks drift and sometimes jump (NTP step, VM pause, a bad container host). The first implementation mixed them: enqueue stamped `run_at` and refilled the rate-limit bucket with the **API server's** clock, while claiming compared `run_at` with the **database's** clock. An API clock 5 minutes ahead made new jobs invisible for 5 minutes; 5 minutes behind ran delayed jobs early and let a tenant exceed its rate limit.

## Decision
Every decision that affects queue behaviour uses the database clock:
- `run_at`, `created_at`, lease expiry, token-bucket refill, API-key expiry, queue-wait measurement, cron "now" are all computed in SQL (`clock_timestamp()` / `statement_timestamp()`) or fetched with `dbNow()`.
- `tests/regression/TestNoApplicationClockInPostgresLayer` fails the build if `time.Now`, `time.Since` or `time.Until` appear in `internal/postgres` (it found 7 violations in the original code). The rare legitimate use (cache TTLs) is annotated `//nolint:appclock` and lives outside that package.
- Application clocks are still used for things that are local by nature: retry-sleep timing, HTTP timeouts, the auth-failure limiter window.

## Consequences
- Skew between servers cannot hide, duplicate or prematurely run jobs.
- The database must be the single source of truth for time; with a replica-based failover, both nodes need sane clocks (monitor with `chrony`).
- Go clocks cannot be skewed from inside a test, so skew safety is enforced **structurally** (the guard test) rather than behaviourally.

## Subtlety: stable vs volatile time functions
`clock_timestamp()` is **volatile**: PostgreSQL cannot use it as an index range bound and can only apply it as a per-row filter. For index-bounded comparisons (the claim query's `run_at <= now`) use `statement_timestamp()`: same database clock, but **stable**, so it can drive an index range. Switching removed an O(backlog) scan (ADR-015). `clock_timestamp()` remains correct for values that are *written* (lease expiry, completion time).
