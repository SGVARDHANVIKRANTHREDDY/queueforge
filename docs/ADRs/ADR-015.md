# ADR-015: Single-Statement Batch Claim with Per-(Queue, Task Type, Priority) Probes

## Status
Accepted (supersedes the per-job claim loop of ADR-003's implementation; the SKIP LOCKED decision itself stands)

## Context
The first claim query scanned the global order `(priority DESC, run_at, created_at, id)` over all queued jobs and **filtered** by queue, task type, due time and tenant slot. Measured on a 2M-row table (`EXPLAIN (ANALYZE, BUFFERS)`):

| Situation | Claim time |
|---|---|
| Normal (history of 2M completed jobs) | 0.15-0.18 ms (flat: the partial index ignores history) |
| 10k / 100k / 400k queued jobs of a task type this worker does not handle, at higher priority | 7.6 / 132 / **653 ms** (`Rows Removed by Filter: 400000`) |
| 10k / 100k / 400k delayed (future `run_at`) high-priority jobs | 24 / 149 / **635 ms** |

Claim cost was proportional to *unrelated* backlog: one worker pool's backlog (or a pile of scheduled reminders) slowed every other pool. Two causes: the filter columns were not in the index's key, and `run_at <= clock_timestamp()` is volatile so it could never be an index bound (ADR-014).

A first attempted fix (probe per priority, one job per claim) made the normal case 5x slower (0.22 -> 1.1 ms) because it paid for ten index probes *per job*.

## Decision
Claim a **batch** in one statement and pay the probe cost once per batch:
1. `cand`: one index probe per (queue, task type, priority) using `jobs_claim_probe_idx (queue_name, task_type, priority, run_at, created_at, id) WHERE status='queued'`; equality prefix + `run_at <= statement_timestamp()` range, so each probe is one index descent. Candidates are pooled (not "one per probe"), otherwise every worker would see the same single top candidate and herd on it.
2. `locked`: `FOR UPDATE SKIP LOCKED` on the candidates, re-checking `status='queued'` under the lock (this re-check is what stops two workers leasing the same job; `TestClaim_ConcurrentWorkersNeverDoubleClaim` fails without it).
3. `ranked` / `free`: number each tenant's candidates in priority order, lock and number its free execution slots (`SKIP LOCKED`: a slot another worker is claiming simply counts as not free).
4. `picked`: pair the Nth job of a tenant with its Nth free slot, highest priority first, `LIMIT n`. A tenant with one free slot and 5,000 queued jobs contributes exactly one job.
5. Data-modifying CTEs mark the jobs running (fresh lease token), reserve the slots and open the attempt rows, atomically.
6. A `meta` row reports tenants with more candidates than free slots; the caller excludes them and runs another round so a noisy tenant cannot hide other tenants' work (max 8 rounds).

## Consequences
- Measured: claim cost flat at ~1-2.6 ms from 0 to 400k unrelated queued jobs (371 buffer hits instead of 403,000).
- Measured: end-to-end drain throughput **+16-20%** versus the per-job claim (698 -> 811 and 618 -> 741 jobs/s) because statements per job fell from ~5 to ~1/8.
- Priority/FIFO order holds across tenants and across batches (`TestClaim_PriorityThenFIFOAcrossBatches`); slot limits are never exceeded under concurrency.
- Cost: one more index (write amplification on enqueue/claim); the old `jobs_claim_idx` is dropped. The migration is `CONCURRENTLY` so it does not block writers.
- **Known remaining limit:** work done per claim is bounded by `candidates + their tenants' pending quotas`: a tenant that is *saturated* (all slots busy) with a huge queue is skipped after one round, but its candidates are still read once per claim. `max_pending_jobs` per tenant bounds this; keep it modest for tenants with low concurrency.
