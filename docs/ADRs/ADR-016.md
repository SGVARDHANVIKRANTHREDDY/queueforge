# ADR-016: Authentication Hardening, Audit Log, and Redacted Worker Visibility

## Status
Accepted

## Context
A review of the authentication path found: (1) an API-key lookup that spawned a goroutine and wrote `last_used_at` on **every request** (write amplification on one hot row; a valid key holder could use it to hammer the database); (2) key expiry decided by the API server's clock; (3) unlimited wrong-key guesses (each costs a hash and an indexed query); (4) no record of who performed control-plane actions; (5) `GET /v1/workers` returned every worker (hostnames, versions, handled task types) to any tenant holding `jobs:read`, disclosing infrastructure and other tenants' task names.

## Decision
1. `last_used_at` is rewritten at most once a minute per key, with at most one update in flight per key (`touching` map).
2. Expiry is evaluated by the database clock inside the lookup query (ADR-014); revoked and expired keys are indistinguishable from unknown keys.
3. A per-client **failure limiter** (20 failures/minute/address, in memory) returns 429 *before* any database work. `X-Forwarded-For` is honoured only when `QF_TRUST_FORWARDED_FOR=true`, i.e. when the API is reachable solely through your reverse proxy; otherwise a client could forge its identity.
4. An **append-only `audit_log`** (database trigger rejects UPDATE/DELETE) records successful control-plane mutations (actor key, route, target id, request id, remote address) via middleware, plus operator actions from the admin CLI. Enqueue is deliberately not audited (the job row is its durable record).
5. `/v1/workers` returns liveness only (id, queues, timestamps, draining) unless the key has `workers:read`.
6. Admin CLI `create-api-key -expires-in` (computed on the DB clock) makes rotation practical: create the new key, deploy it, revoke the old one.

## Consequences
- Each decision has a test, and each test was mutation-checked (the vulnerability re-introduced; the suite fails).
- The limiter is per process: N API replicas allow N times the limit (still a hard cap). A global limit belongs at the reverse proxy.
- Audit writes are synchronous on control-plane requests (rare); a failed audit write is logged loudly but does not fail an action that already happened.
